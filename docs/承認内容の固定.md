# 承認内容の固定

現行QE_BUILDでは、GatewayのHTTP、CLI、資料整理から既存Approval Gateへ入るcommand内容を固定し、Executorまで同じ内容digestで照合する。HDSが発行した元objectの内部plan対応を保持したまま、引数、宛先、許可constraints、目的・commit、command IDを深く固定する。

HTTPのpending承認は固定したcommandと内容digestを保持する。通常の承認画面・resume入口を使い、以前の承認を別内容へ転用しない。plan改訂で影響する旧pendingの失効、既存のL3最終レビュー、Approval Gate、tool側のsandbox検査は継続する。

Executorへ渡す承認済みcommandは独立した固定copyである。authority instance、proof、内容digest、消費状態はprivate WeakMapに置く。JSON保存やobjectのpropertyコピーでは実行権限を複製できない。同じ承認の二度目の呼出しはadapter前に拒否する。失敗した呼出しの承認も復活せず、新しい採否を必要とする。

内容digestは既存の制限JSON・JCS境界から作る。値をJSON種別付きで表現し、小数のtemperatureなどは数値文字列として固定する。数値、文字列、object、arrayを区別し、既存境界の整数制限を緩めない。getter、関数、非有限数、安全整数範囲外の整数、負のゼロ、危険key、不正Unicode、深さ・容量違反は受理しない。JSON key順序は同一内容となるが、文字内容をUnicode正規化して別内容と同一化しない。既存の宣言済みoptional fieldのundefinedだけは省略し、tool実引数やnoop理由等のundefinedは非JSONとして拒否する。拒否理由にはraw引数を含めない。

これはApproval受付からExecutorまでの内容固定と同一process内の単回承認の接続である。D02.01全体の委任・目的版・実体版・issuer/audienceの結合、D02.02のprocessを越える認証済みticket・期限・永続消費、独立Broker PermissionはBUILD_GAP。再起動後の作用照合やreceiptは次のconsumerであり、このWeakMapを永続ticketの代替としない。内容digestだけで発行者・本人認証、現在の権限を成立させない。

実provider、実資格・外部業務作用、別repo編集、5OS・installed製品、QC／QA、公開・出荷の証拠はこの接続に含まない。現在の到達点と次consumerは[現行指示](IMPLEMENTATION_INSTRUCTIONS.md)、実際の確認結果は[開発進捗](開発進捗.md)を参照する。
