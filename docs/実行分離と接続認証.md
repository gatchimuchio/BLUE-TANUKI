## 2. 最小接続と認証の選定

既存の保護されたnative IPCと登録済みAdapter機構を優先する。BLUE側の接続境界が契約を検証し、外殻側の限定Adapterが既存Broker操作へ接続する。Owner credentialをJやCへ渡して接続を成立させない。BLUEの参照Adapterは実native接続済みではなく、実登録・通信・対応操作はD03.01/.02で確認する。

認証主体・役割・owner・host・許容runtimeを保護された登録簿から取得し、issuerとaudienceをその主体へ束縛する。登録簿の変更・接続許可は必要なOwner承認を持つ。bodyの自己申告、共有Bearer、PIDだけ、過去のUI表示を根拠に権限を昇格しない。接続先の認証と登録内容を確認するまで秘密や承認内容を送らない。

受領Brokerが高エントロピーのopaque handleを発行し、保護された受領記録へ照合する方式を選ぶ。handleの所持だけで実行しない。登録済みissuer/audience、現在のPermission、必要なOwner Approval、内容digest、期限、世代、未消費状態を実使用直前に再検証する。接続認証は人間同意でもPermissionでもない。

既存IPCの限定拡張で認証主体の結合を満たせない具体的理由が出た場合だけ、新transportをD03.03の限定差分候補にする。候補は局所TLS 1.3の相互認証と登録簿の結合であり、独自署名方式を作らない。TLSのclient認証やearly dataの再送特性は[RFC 8446](https://www.rfc-editor.org/rfc/rfc8446)に照合した。この候補でも証明書の認証はPermissionを発行しない。0-RTT・未認証fallback・bodyによる相手の置換を許さない。今回はendpoint作成や外部公開を承認していない。

| 結合する内容 | 実使用時に拒否する条件 |
|---|---|
| issuer／audience、owner、host、runtime、workspace登録hashと実体 | 未登録、別主体、別host、登録変更、実体差替、自己申告だけ |
| task／run／goal version、session generation、execution epoch | 別仕事、旧session、古いworker、restart前handle、fencing不一致 |
| contract／canonical version、内容・対象・実行条件・依存digest | 未対応版、変換後内容の不一致、対象変更、依存失効 |
| approval用途、budget、deadline、失効、単回消費、receipt | 用途違い、期限切れ、失効、既消費、結果不明を新規実行として再送 |

session generationは接続寿命、execution epochは仕事の実行世代として分ける。再起動後は旧handleを失効し、再登録と正本receipt照会を行う。同一request_id・同一bytesの再送は既存receiptを返し、内容差替は拒否する。ACK不達やreceipt不明は結果不明であり、別IDで再実行しない。期限・鍵取得不能・失効状態の確認不能はfail-closed。登録更新やGit復元から現Permissionを推定しない。

## 3. 承認内容の正規化と凍結

交換内容は版を持つ制限JSON profileとし、RFC 8785 JCSのcanonical UTF-8 bytesへ変換する。JCSは文字列をそのまま保持し、object keyをUTF-16 code unit順へ整列する。[RFC 8785 §3](https://www.rfc-editor.org/rfc/rfc8785#section-3)の仕様参照であり、現BLUEや外殻がこのprofileに適合済みという主張ではない。

- raw UTF-8段階で不正encoding、重複key、孤立surrogate、上限超過を拒否する。重複を消す通常parseの後では検出したと扱わない。未知field・未対応版・危険keyもschemaで拒否する。
- JSON numberはsafe integer範囲の通常十進整数tokenだけとする。小数・指数・負のゼロ・丸めを要する入力を変換前に拒否する。高精度金額・大きい整数はschemaで指定したcanonical十進文字列に限り、暗黙coercionをしない。
- array順、nullと省略の違い、文字列、改行を保持する。NFKC、trim、改行変更、未知field削除、undefinedの省略、循環placeholder化をしない。timestampはschemaが定めるUTCミリ秒表記を検査し、異なるzoneを黙って読み替えない。
- digest対象は版、主体・世代・仕事、内容・対象・条件・依存・承認用途・budget・deadlineを持つ凍結内容。計算後digestとopaque handle自体は対象外とし、自己参照を作らない。SHA-256を同じcanonical bytesから計算する。
- 検査したbytesと実行内容を一致させる。変換が必要なら、変換契約・変換先digest・対象・条件を承認へ結ぶか、再レビューする。表示用digestやparsed objectの後変更で代替しない。

C01.02でTypeScript／Rustの同値vectorを実consumerへ接続する。D02.01/.02はraw拒否・内容結合・issuer/audience・期限・旧世代・再送を実通信で検証する。既存NFKC試験や外殻独自payload hashの成功だけで同値を閉じない。

## 4. 非信頼実行と保護経路の故障分離

J/Mは信頼側の制御processに置き、B03.01の別所有・別更新APIを維持する。C、third-party tool、browser、外部agentなどは別worker processと実効OS制約へ置く。raw DB、Owner credential、汎用秘密、policy書換え能力を渡さず、現在の限定射影と要求入口だけを与える。別cwdやprocess分割だけでOS隔離済みとしない。

保護監督はJ/Cのevent loop、通常queue、SQLite応答から独立したprocessと制御入口を持つ。J/C停止、DB障害、queue飽和でも期限切れ・失効・遮断・kill・状態保全へ到達できる構造にする。保護は新目的、Permission、grant、fallback authorityを生成しない。認証されたOwner停止または事前に採否した保護条件だけを扱い、任意Cから全体停止を命令させない。

停止を通常audit書込みの成功待ちにしない。保存不能時は外部作用を止め、限定緊急記録を保全し、復旧後に欠損として照合する。hash-chainの成功記録を捏造しない。外部先が受領済みの場合は取消要求と外部取消確認を区別する。

| 観測状態 | 言える範囲と次の動作 |
|---|---|
| 停止要求済み | kill／取消要求を出した。実停止は未確認。新しい作用を保留し照会する。 |
| worker terminal | 当該workerの終端を観測した。子孫processや外部取消完了は別確認。 |
| process群停止確認 | 対象OSで隔離境界内の全子孫終了を確認した。外部受領済み作用は残り得る。 |
| 外部取消確認／結果不明 | 実receiptで取消を確認するか、未決作用として保全・照会する。自動再実行しない。 |

WindowsのJob Object等、POSIXのprocess group等は対象OS別の実証を要する。D05で独立停止と保存障害下停止、D07でOS上の実効隔離・子孫停止を検証する。今回の文書検査で停止成功を主張しない。復帰は原因修復、新世代、現Permission、対象、receiptの再照合を要し、人間resumeも前提修復を迂回しない。

## 5. 秘密参照と外向き作用

既存暗号化storeの保存機構を再利用する。秘密は用途限定参照とし、owner、host、接続先、目的、action、scope、期限、版、失効をBroker側で実使用直前に検査する。秘密値は信頼されたBroker connectorが必要な間だけ解決する。J/C、通常子processの汎用env、汎用IPC、UI、auditへ値を展開しない。既存process.env展開の切替はD06の対象であり、今回実装済みにしない。

read、計算API、添付、URL、診断にも外向き情報を含み得る。Cの提案やadapter metadataから資格・送信許可を作らず、宛先・内容・現在権限を検証する。秘密値のhashも公開安全性の証明ではない。ログには参照IDと必要な非機密metadataだけを記録し、失効・取得不能では作用を止める。

## 6. 外殻固有権限の一般射影

| 外殻で独立している対象 | BLUEへ渡す意味と所有者 |
|---|---|
| Runtime／Workspace登録 | 相関と対象確認の証拠。環境Brokerが現登録を照合し、アクセス許可へ昇格しない。 |
| UI intent／表示確認 | Ownerの要求・見た内容の証拠。Jの採否やBroker Permissionそのものではない。 |
| J採否 | 内容・条件・世代に結合する採否証明。GUI-Shell Permissionを発行しない。 |
| Permission／Owner Approval | 環境Brokerが現Permissionと必要なOwner Approvalの条件を別々に検証し、結合したgrantを排他区間で一回消費する。二重消費や部分消費を成功としない。 |
| 本文露出承認 | 外殻の表示・露出境界。同意用途を実行承認へ流用しない。 |
| 取消要求／terminal／receipt | 取消受付・局所停止・外部結果を別状態で帰還し、表示成功から確定を推定しない。 |

実作用は **J採否 AND 環境Brokerの現在Permission AND 必要なOwner Approval**。一つのUI確認で複数契約を適切に束縛しても、証明の責任とtoken用途を混同しない。unsupported操作は実行せず、通常buildでのTaskをfixture条件だけで昇格しない。HDS-BRAIN standalone、Approval Gate、L3、既存brand、監査、Runtime Invariantsを移行中も保つ。

## 8. 反例、復元、公開境界

方式に反例が出たら元の意味・失敗・証拠を保持し、該当契約とconsumerだけを再開放する。接続失敗は認証、期限、世代、内容、Permission、停止未確認を区別し、未決作用の照会方法を示す。Git復元はコード・資料の復元であり、鍵失効、既消費権限、実データ、外部作用を巻き戻さない。
