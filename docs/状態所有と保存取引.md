## 2. 最小の配置と更新API

配置と実装状態を区別する。C03.01で作ったM APIはpackage barrelとproduction consumerに接続しておらず、J側APIは後続施工である。

| 配置 | 所有者・更新API | 消費する経路 | 保存・拒否・受入先 |
|---|---|---|---|
| `packages/protocol/src/状態更新契約.ts` | strict `MemoryCommit` V1/V2、receipt schema、canonical digestと境界検査。V2は期待版をdigestへ結合 | protocol barrelから型/関数として利用可能。権限consumerなし | C03.01/02局所test。V1は履歴読取用、schema自体は採否権限を持たない。 |
| `packages/hds-brain/src/記憶更新.ts` | **M** 内部API。J-owned approval readerを必須にし、commit/receipt/snapshot/verifyを渡す | J coordinatorだけが局所利用。HDS barrel、Controller、Gateway、UIから未接続 | C03.01–03局所test。J readerは合成fixtureで、実認証・実承認の証明ではない。 |
| `packages/hds-brain/src/保存取引.ts` | **M** SQLite取引。期待版比較、同内容retry、異内容ID拒否、event/record差分/revision/update消費/receiptを一transactionで確定。私有root内path resolverをJと共有 | internal `MemoryUpdateLedger` だけが使用。下流へDB handle/SQLを渡さない | file DB、設定読戻し、V1/V2 chain/state replay、合成fault injection。Gateway組立はない。 |
| `packages/hds-brain/src/制御状態.ts` | **J** 専用 `j_events / j_state / j_pending`、不透明pending参照、M receipt再照合、J revision帰還 | internal `JMemoryCommitCoordinator`がM SQLite transactionと局所接続。package barrel、Controller、Gateway、UIから未接続 | C03.03は合成承認reader・一時file DBでclose/reopenを試験。production J authority sourceは未実装。 |

Jは目的射影・採否・制御状態を所有する。Mは意味記憶・経験・関係を所有し、承認内容だけ反映する。同じDBを使っても、所有者、更新API、取引、アクセス境界は別である。共有schemaだけでは実効アクセス制御や故障分離は成立しない。それらはB03.02と後続の実経路で検証する。

本書の可変意味記憶Mは、既存Trinityのdeterministic policyを表す `M` と別概念である。後者のpolicyを記憶更新で書き換えない。記憶を根拠・経験・文脈として利用できるが、過去の承認記録から現在のPermissionやApprovalを作らない。`memory_used_for_authority=false`、`complete_history_used_for_authority=false` を維持する。

HDS-BRAINの許容依存は既存規定どおりNode built-ins、protocol、局所のpure modules。gateway、外部client、doctor／repairをcoreからimportしない。環境Permission、単回消費、実行receiptの正本は当該環境Brokerに残す。J/MのDBへ一括移管しない。

## 3. 保存方式の決定と証拠の限界

新J/M正本には **一つのローカルSQLite DB** を使う配置決定を維持する。C03.01はM APIへ明示的に渡した絶対pathを指定私有root配下へ閉じ込め、実pathとparent directoryを解決してsymlink後のroot外pathも拒否する。production既定path、環境変数、Gateway設定は追加していない。局所testは一時file-backed DBを使い、旧audit・会話sessionとは別にした。実運転用の私有rootへの接続やsecret移行はない。

配置上のJ namespaceは `j_events / j_state / j_pending`、M namespaceは `m_events / m_state / m_updates / m_receipts`。C03.01はM側に `m_schema` と `m_records` を加え、C03.03はJ側に `j_schema` と上記J namespaceを実装した。両側のevent・stateは別の所有者・API・transactionを持ち、同じ物理DBであることを全体ACIDや故障分離と読み替えない。J storeは承認sourceからID・event・digestが一致する参照を検証してから最小metadataだけをpendingへ保存する。合成test readerはJの現採否を立証しない。

`m_events` はM状態を再生するため確定した差分とsemantic valueを保持するM所有の正本eventである。HDS一般 `AuditLog`、CompleteHistory、外部向け表示projectionではなく、HDS auditへpayloadを複製しない。schemaは任意のJSON valueを許すため、production inputからcredential等の機微値を排除する経路も今回未接続である。テストは合成値だけを使った。

driverはNode built-inの `node:sqlite` / `DatabaseSync`。C03.01のWindows host Node `22.23.3` で実際に開き、書込み、fault rollback、close/reopenを行った。ExperimentalWarningは観測されており、同版の[公式文書](https://nodejs.org/download/release/v22.23.3/docs/api/sqlite.html)もexperimentalとする。APIは同期実行である。Vitest 2.1.9/Viteは静的 `node:sqlite` を `sqlite` として解決し失敗したため、Node標準 `createRequire` から同一built-inを読み込む。backend/shim/fallbackは増やしていない。Node `22.14.0` minimum上の受入、製品経由の設定接続、kill/crash耐久性は未実施。constructor timeout等の22.16追加APIは使わない。

選定設定は `journal_mode=DELETE`、`synchronous=EXTRA`、`foreign_keys=ON`、`busy_timeout=0`、extension無効。接続時に値を読戻し検査し、値はparameter bindingで渡す。`BEGIN IMMEDIATE`内でapproval参照、event、record変更、revision、更新ID、receiptを処理し、trigger faultを各永続書込み点へ注入した。試験では失敗後に事前snapshot・receipt・event chainが維持された。[SQLiteの同期設定](https://www.sqlite.org/pragma.html#pragma_synchronous)と[原子commitの説明](https://www.sqlite.org/atomiccommit.html)は保存系の仕様根拠であり、仕様記述またはlocal testをOS crash耐久性へ昇格させない。

C03.01の合成fault/reopenは、C03の稼働障害・kill/crash・破損・再構築・最小Node版・対象OS/保存媒体受入の代替ではない。schema/tableの内部整合性とevent/receipt/state replayは検査するが、認証済み外部anchorがなくDB全体の置換を検出しない。設定失敗時に `OFF`、`MEMORY`、旧JSONLへfallbackしない。DB共有は独立停止の可用性を保証しない。

不採用は、連続JSONLを全状態の原子取引とする方式、権限と意味記憶の共通可変辞書、既存の横に置く万能control framework、環境Brokerまで一DBへ入れる方式である。反例が出た場合は旧決定と失敗を保持し、該当するdriver・journal設定・契約・試験だけREPLANする。必要ならstandalone制約を守る検査済みSQLite binding等へ再選定し、原子性・同期条件を弱めない。製品データで試行しない。

## 4. 確定単位と帰還

同じDBでもJ採否、M反映、J帰還を一つの巨大取引にしない。所有範囲内の確定と、別主体からの結果照合を区別する。

| 取引 | 入力・実検査 | 一緒に確定するもの | 結果・失敗時の状態 |
|---|---|---|---|
| J採否取引 | 現委任・目的版、job所有者、event ID、期待J revision、採否対象 | 制御event、次J状態／revision、更新ID・内容digest・期待M revisionを持つ `memory_commit_pending`／送信記録、不可欠な監査event | 配置契約。C03.03のstageは合成J readerで参照を検証するが、production Jの採否取引ではない。 |
| M反映取引 | V2 `MemoryCommit` schema/digest、J readerからの3要素一致参照、transaction内の現在M revision | M event、record差分、次M revision/event head、update ID消費、receiptをSQLite transaction内で確定 | **全反映または全未反映**をC03.01/02/03のfixture/fault試験で確認。未使用IDの期待版不一致と同ID異内容を拒否し、同ID同内容はJ照合後に保存済みreceiptを返す。 |
| J帰還取引 | 更新IDで照会したM receiptの同一性・内容・版、現在pendingと期待J revision | receipt参照、pending解消、次J revision、J event | C03.03では局所coordinatorが `MemoryUpdateLedger.verify()` / `receipt()` の読取だけを行い、receipt不在はpending維持、不一致はblocked、正しいreceiptはJ event/state/pendingを一transactionで確定する。Controller/Gateway production consumerは未接続。 |
| 環境Broker開始取引 | 現在ticket、実体・内容・前提、権限、世代、期限、予算、未消費 | 単回消費、開始意思、不可欠な開始監査 | Broker側の別所有・別取引。commitとspawnの間のcrashは検査対象。推測で未消費へ戻さない。D04.01で実装・受入。 |

J/M間でDBが別になる変更では単一ACIDを仮定せず、同じ更新ID、outbox/inbox、期待版、再送、receipt照会を維持する。通信再送と非冪等な業務作用再送は別であり、内部の重複排除で外部作用のexactly-onceを保証しない。

新しい正本監査eventはraw本文を持たず、digest、出所、版、ID、時点、状態を持つ。旧JSONLへ投影するときは正本sequence/cursorと重複検査で追跡する。既存連鎖の意味と検証を維持し、投影失敗を記録する。投影成功前に「旧監査まで保存済み」と表示せず、欠損を架空の完全連鎖で埋めない。認証済み末尾anchorのないhash-chainが全差替え・末尾切落しを必ず検出するとは主張しない。

## 6. 有限受入と公開保管

今回までの局所受入は、M transactionとJ pending/receipt照合の実コードを一時SQLiteで通し、証拠限界を識別できること。C03.03の実test consumerは `JMemoryCommitCoordinator` → J `j_*` transaction / M `MemoryUpdateLedger` → M receipt readで、承認sourceのみ合成fixtureである。証拠源は `FIXTURE` / `INTERNAL_STATE` でありproduction consumerの証拠ではない。「同じDBだから同じ最終責任」「memory receiptだから現在権限」「局所close/reopenだからOS crash耐久」という読み替えをしない。

証拠源は配置の `CONFIG`、公式Node/SQLite文書の `EXTERNAL_EVIDENCE`（仕様記述の範囲）、局所実SQLite transactionと合成入力の `FIXTURE`。稼働製品の `LIVE_RUNTIME` ではない。必須workspace検証と未実施条件は [開発進捗](開発進捗.md) に記録する。親C03/B03全体の実接続・障害・復帰scenarioは完了していない。

変更は本配置と関連する工程記録だけ。復元点は編集前main `c5659dc`、前世代 `d8f988a`。通常成果を検証しGitHubへ履歴・成果物として保存する。私有原典・封印詳細・完全対応表・秘密・運転状態・raw証拠は掲載しない。P13、J0/J1、版、公開主張の状態は変更しない。
