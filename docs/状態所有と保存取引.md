## 2. 最小の配置と更新API

次の四つは **新設予定のpathであり、現時点では存在しない**。既存package・入口へ接続する設計を固定したもので、空classや並行runtimeを作る許可ではない。API名は後続実装で型・呼出し・拒否試験へ接続する。

| 配置予定 | 所有者・更新API | 消費する経路 | 保存・拒否・受入先 |
|---|---|---|---|
| `packages/protocol/src/状態更新契約.ts` | 交換契約の正本。制御event、期待revision、`MemoryCommit`、記憶receipt、更新IDと内容digest | 既存 `index.ts` からJ/M・gatewayへ接続。C01.01／C01.02 | schema・出所・版・同一性の検査。契約は採否権限を持たない。 |
| `packages/hds-brain/src/制御状態.ts` | **J**。期待revisionとjob所有者を確認する制御更新API、pending照会・帰還API | 既存 `HDSUpperController` の採否・再開経路。UIやCはwriterでない | J取引とJ帰還取引。stale revision、所有不一致、保存失敗を拒否。C01／C03.03、E03。 |
| `packages/hds-brain/src/記憶更新.ts` | **M**。J承認付き `MemoryCommit` の反映APIと更新IDによるreceipt照会 | Jが採った変更だけを消費。Cの案を直接確定しない | M取引。同ID異内容・期待版不一致・承認不一致を拒否。C03.01–04。 |
| `packages/hds-brain/src/保存取引.ts` | J用とM用の限定port。所有者ごとの取引を提供し採否しない | 上記二つの内部APIだけ。gatewayは設定注入と組立 | 新J/M用SQLite。汎用SQL、DB handle、全状態書換APIをC・UI・pluginへ渡さない。C03。 |

Jは目的射影・採否・制御状態を所有する。Mは意味記憶・経験・関係を所有し、承認内容だけ反映する。同じDBを使っても、所有者、更新API、取引、アクセス境界は別である。共有schemaだけでは実効アクセス制御や故障分離は成立しない。それらはB03.02と後続の実経路で検証する。

本書の可変意味記憶Mは、既存Trinityのdeterministic policyを表す `M` と別概念である。後者のpolicyを記憶更新で書き換えない。記憶を根拠・経験・文脈として利用できるが、過去の承認記録から現在のPermissionやApprovalを作らない。`memory_used_for_authority=false`、`complete_history_used_for_authority=false` を維持する。

HDS-BRAINの許容依存は既存規定どおりNode built-ins、protocol、局所のpure modules。gateway、外部client、doctor／repairをcoreからimportしない。環境Permission、単回消費、実行receiptの正本は当該環境Brokerに残す。J/MのDBへ一括移管しない。

## 3. 保存方式の決定と証拠の限界

新J/M正本には **一つのローカルSQLite DB** を使う。設定で与えられる私有状態root配下の `state/jm/canonical.sqlite` を予定pathとし、旧audit・会話sessionの保存先と分離する。今回はDBも新しい環境変数も作成していない。secret実値をDBや監査へ移す設計ではない。

J namespaceは `j_events / j_state / j_pending`、M namespaceは `m_events / m_state / m_updates / m_receipts`。所有者の不可欠な監査eventはそれぞれの確定取引に含める。table名は配置のラベルであり、下流へのSQL公開契約ではない。Jの現在採否をMが検査する際も、限定された読取参照を使いJ状態のwriterにはならない。

driverはNode built-inの `node:sqlite` / `DatabaseSync` を選ぶ。現在のNode `22.23.3` でimportとclassの存在、ExperimentalWarningを観測した。DBを開いたり書いたりした結果ではない。同版の[公式文書](https://nodejs.org/download/release/v22.23.3/docs/api/sqlite.html)もexperimentalとし、APIは同期実行である。既存のNode `22.14.0` 以上という基準は変更せず、文字列path・基本prepare/execを使う。22.16追加のconstructor timeoutやbackup APIに依存しない。最小対応版での実driver受入は未実施。

選定設定は `journal_mode=DELETE`、`synchronous=EXTRA`、`foreign_keys=ON`、extension無効。開いた接続で値を読戻し検査し、内容はparameter bindingで渡す。lock待ちは有限にし、同期呼出しの遅延を独立停止経路へ持ち込まない。[SQLiteの同期設定](https://www.sqlite.org/pragma.html#pragma_synchronous)は、EXTRAがDELETE modeでjournal削除後のディレクトリ同期を追加すると説明する。[原子commitの説明](https://www.sqlite.org/atomiccommit.html)は保存系の前提も含むため、仕様確認をこのhostの耐久性証明へ昇格させない。

C03で実transaction境界、write/sync失敗、再起動、破損、最小Node版、対象OS・保存媒体を確認する。未成立なら当該profileで新作用を開始しない。設定失敗時に `OFF`、`MEMORY`、旧JSONLへ黙ってfallbackしない。DB共有は独立停止の可用性を保証しない。

不採用は、連続JSONLを全状態の原子取引とする方式、権限と意味記憶の共通可変辞書、既存の横に置く万能control framework、環境Brokerまで一DBへ入れる方式である。反例が出た場合は旧決定と失敗を保持し、該当するdriver・journal設定・契約・試験だけREPLANする。必要ならstandalone制約を守る検査済みSQLite binding等へ再選定し、原子性・同期条件を弱めない。製品データで試行しない。

## 4. 確定単位と帰還

同じDBでもJ採否、M反映、J帰還を一つの巨大取引にしない。所有範囲内の確定と、別主体からの結果照合を区別する。

| 取引 | 入力・実検査 | 一緒に確定するもの | 結果・失敗時の状態 |
|---|---|---|---|
| J採否取引 | 現委任・目的版、job所有者、event ID、期待J revision、採否対象 | 制御event、次J状態／revision、更新ID・内容digest・期待M revisionを持つ `memory_commit_pending`／送信記録、不可欠な監査event | 永続pending。M反映済みとは表示しない。未commit確認済みとcommit結果不明を分け、後者は同一event／更新ID・revisionで正本を再読し、確認まで新作用を止める。 |
| M反映取引 | 実際に有効なJ採否と内容digest、期待M revision、update IDの消費状態 | 意味記憶event、次M状態／revision、更新ID消費、同一receipt、不可欠な監査event | **全反映または全未反映**。同ID同内容は元receipt、異内容は拒否。commit後だけreceiptを返す。 |
| J帰還取引 | 更新IDで照会したM receiptの同一性・内容・版、現在pendingと期待J revision | receipt参照、pending解消、次J revision、不可欠な監査event | reply消失を未反映と推定しない。未commit確認済みならpendingを保持。commit結果不明なら同一ID・revisionでJ正本を再読し、確認まで新作用・再反映を止める。 |
| 環境Broker開始取引 | 現在ticket、実体・内容・前提、権限、世代、期限、予算、未消費 | 単回消費、開始意思、不可欠な開始監査 | Broker側の別所有・別取引。commitとspawnの間のcrashは検査対象。推測で未消費へ戻さない。D04.01で実装・受入。 |

J/M間でDBが別になる変更では単一ACIDを仮定せず、同じ更新ID、outbox/inbox、期待版、再送、receipt照会を維持する。通信再送と非冪等な業務作用再送は別であり、内部の重複排除で外部作用のexactly-onceを保証しない。

新しい正本監査eventはraw本文を持たず、digest、出所、版、ID、時点、状態を持つ。旧JSONLへ投影するときは正本sequence/cursorと重複検査で追跡する。既存連鎖の意味と検証を維持し、投影失敗を記録する。投影成功前に「旧監査まで保存済み」と表示せず、欠損を架空の完全連鎖で埋めない。認証済み末尾anchorのないhash-chainが全差替え・末尾切落しを必ず検出するとは主張しない。

## 5. 故障、復元、次の実装

| 条件・未達 | 今回固定した動作／限界 | 実装・証拠を受ける先 |
|---|---|---|
| revision競合、同ID同／異内容 | 一仕事一確定経路。期待版と内容を照合し、競合・異内容を拒否 | C03.02、E03.01／02。既存MapやPromise鎖を代替証拠にしない。 |
| M commit後にreply消失／J再起動 | pendingとreceipt照会で反映有無を確定。新IDによる再反映をしない | C03.03、E03.02。未決状態は表示に残す。 |
| write、sync、disk full、schema、破損、不正所有者 | 原因を区別し新作用を停止。進行中の危険なprocessの停止をDBやaudit成功に依存させない | C03.04、B03.02。停止の独立性は別の実機証拠を要する。 |
| 旧新のwriter・epoch・状態切替 | 今回は切り替えない。shadowから外部作用やM正本更新を二重に流さない | B03.03、E03。schema互換・未決作用・消費済み権限を照合。 |
| restore／旧binaryへ戻す | コード復元、保存状態復元、権限消費、外部作用の補償は別 | B03.03、C03.04、E03。過去承認を現在許可として復活させない。 |
| 同期driverでJ queueが詰まる | DB共有を故障分離に読み替えない。保護側は同じqueueやDB commitを待たず失効・遮断する | B03.02、E03。実効OS境界と停止を検証。 |

新Mの試験は、全反映／全未反映のfault point、期待版競合、同内容再送・異内容拒否、reply消失、再起動照合、保存・同期失敗と派生像再構築を消費する。これらは **NOT_RUN**。既存controllerの記憶capture・非権限参照、audit／LTM／complete-historyの破損chain拒否、grant保存、session再読込、recovery／update試験は旧境界の回帰であり、新しい取引の成功証明ではない。

## 6. 有限受入と公開保管

今回の受入は、既存資産の採否、所有者・consumer・更新API、保存方式、確定単位、失敗・再試行・復元、後続の試験先が具体化すること。「同じDBだから同じ最終責任」「記憶だから現在権限」「旧hash-chainだから複数保存が原子」「並行する第二正本」「仕様確認だからhost crash実証」という資料案は拒否する。

証拠は公開ソース・配置決定の `CONFIG`、公式仕様の `EXTERNAL_EVIDENCE`（仕様記述の範囲）、資料負例の `FIXTURE`。必須ワークスペース検証は [開発進捗](開発進捗.md) に実コマンドと結果を記録する。親B03の全実接続・障害・復帰scenarioを完了したとは扱わない。

変更は本配置と関連する工程記録だけ。復元点は編集前main `c5659dc`、前世代 `d8f988a`。通常成果を検証しGitHubへ履歴・成果物として保存する。私有原典・封印詳細・完全対応表・秘密・運転状態・raw証拠は掲載しない。P13、J0/J1、版、公開主張の状態は変更しない。
