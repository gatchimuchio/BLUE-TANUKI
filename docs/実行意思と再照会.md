# 実行意思と再照会

現行GatewayのHTTP、CLI、資料整理は、既存Approval内容固定から私有の実行storeを通してExecutorを呼ぶ。保存先はBLUE_TANUKI_STATE_ROOT配下のprivate-state/execution-intents/executor.sqlite。通常file操作からのprivate-state拒否を維持し、資格・C応答・汎用command本文は保存対象にしない。計画に結合した組込みfile.searchの実検索結果と元のoperation_core_resultだけを、限定した私有outboxへ保存する。

承認コピーの発行時に、command IDのdigest、全内容digest、proof digest、authorityごとの起動epoch、発行時刻と期限を結合する。発行から実adapter呼出しまでの期限は通常5分であり、実行中のtimeoutとは別。同一command IDの新proof発行も拒否する。再試行には現在のHDS・Approvalから新commandの採否が必要であり、再送で期限を更新しない。既存pending承認の期限・本人review条件は継続する。

Executor入口では既存authority・内容・L3を検査し、wallとprocess内monotonic期限を別々に確認する。その後、単回消費、開始意思、canonicalな開始eventをSQLiteの同一取引で確定する。実adapterを呼ぶ直前にも期限とepochを確認し、呼出し試行の記録を保存する。LLMのhistory読取待機後にもこの確認を行う。保存失敗や時計巻戻しでは下流を呼ばない。

実行後は未呼出し、adapter応答の観測、結果不明を区別して保存する。adapter_returnedはadapterのsuccess応答を観測した記録であり、外部受理・postcondition・目的成功の保証ではない。console_previewも外部送信の証拠ではない。receipt保存失敗では成功を返さず、同じ承認を復活させない。消費後にprocessが中断して未完記録が残った場合は、起動の証拠不足を未実行へ変換せず、照会でoutcome_unknownと表示する。

Control Centerが使う既存GET /runtime/snapshotにはexecution_receiptsを追加した。既存inbound Bearerで認証し、最大50件のdigest・状態・worker観測metadataを返す。再起動後も同じ保存記録を表示でき、照会は作用も権限復元も起こさない。issuedは過去の発行記録であり、現在の実行可能性を表さない。used_for_authority=false、execution_eligible=falseを維持する。raw ticket handle、actor、payload、path、credentialは返さない。

起動と各書込み・snapshotは一貫したSQLite取引でevent chainと最新receiptの整合を確認する。eventの破損・欠落から作用へ進めない。これは私有保存状態の整合確認であり、hashやDBが発行者を認証するわけではない。event全列の確認による長期運転時の費用・容量・保持方針は後段QCの対象として残す。

## 組込みfile.searchの専用worker

Gatewayの通常HTTP・CLI入口では、登録された組込みfile.searchだけを固定built childへ送る。先に永続開始意思を保存し、Nodeが継承する親所有の専用IPCで通信する。任意module、shell、plugin registry、親の起動loader、資格を含む全envは渡さない。childが返すreadyを親のchild.pidと照合し、毎回新しいworker ID・実PID・OS・起動時刻を同じticketへ保存する。digestやPID番号だけを認証根拠にしない。同名custom adapterを組込み実装へ置換しない。

readyは検索開始ではない。worker記録・呼出し試行の保存を含む待機後、IPC送信直前にもwall／monotonic期限とGatewayの現在停止条件を確認する。childは一要求だけを受け、内容digest・ticket・epoch、file.searchの固定能力、現在のFILE_ROOTと既存のroot・秘密領域保護を検査する。親は結果の容量・形状・元command／ticket／worker／epochを照合し、実closeを観測してから結果を返す。起動待ちは最大10秒、実行はcommandのtimeout（省略時30秒）、結果受領後の終了待ちは最大5秒とする。これらは実装上の上限であり、安全停止の保証値ではない。

Gatewayのemergency stopはworkerのAbortSignalを監査保存より先に発火する。通常終了処理もworkerと最終receiptを待ってからDBを閉じる。切断・失敗・取消・期限では親が所有するchildだけを停止し、必要時に強制停止してcloseを待つ。結果は既存Executorのoperation_core_resultからJへ戻り、既存result_equalsによる検証を通った結果だけが依存stepへ使われる。実exitの保存失敗を成功へ変換しない。

snapshotのworker_id_digest、worker_pid、worker_platform、worker_exit_observedは観測用metadataであり、現在の実行資格や全process群停止を表さない。再起動後も保存receiptを照会するだけで、workerやticketを復活させない。file_search_worker_failedではFILE_ROOT、対象、receiptを確認する。file_search_worker_timeout／disconnectedでは結果不明を確認し、同じ仕事を自動で再送しない。fixed childがない場合は通常のpnpm buildを行い、別実行路へfallbackしない。

## 保存結果の再起動後調停

通常HTTPの計画stepでは、承認後・実行前にExecutorの発行ticket、内容・proof digest、起動epoch、期限をJの私有bindingへ結合する。ExecutorとJの内容digestは異なる契約なので直接比較せず、Gatewayで固定commandから照合する。Jの保存失敗では作用へ進めない。

固定workerの実結果をreceiptと同じ取引でexecution_result_outboxへ保存する。保存するのは検索のroot・query・件数・matchesと元の実operation_core_result、status・duration、既に結合したadmissionに限る。C候補、意味更新、raw errorを含めない。検索本文は私有情報として扱い、snapshotやComplete Historyに返さない。既存output_digestはJSONのキー順に依存するため、保存・配送で元JSONの順序を保持する。

起動時と通常の計画実行後に、保存上限1000件内の全pendingを一度走査する。Jは元bindingの開始意思とadmission、request／command／commit／payload、実結果digestを照合し、既存result_equalsによって検証する。再起動時に失われたinflight・承認は再構成しない。missing、issued、selected、invalidatedから開始意思を推定しない。結果は元revisionへ帰属し、元の観測時刻＋10分の鮮度を保つ。遅れた結果は観測として保存できても、期限切れの依存入力を再び有効にはしない。

Jの結果と配送digestは同じcheckpoint CASで保存し、その後にExecutor側へackする。J commit後・ack前で中断した場合は同結果の再送でackを回復し、結果を二重登録しない。同ticketの異内容や別epochは拒否する。再配送はworker起動・承認・外向き送信を呼ばない。通常onFeedbackのinflight保護も維持する。

snapshotのresult_delivery_digestとresult_delivery_acknowledgedは配送観測だけ。未確認の配送はpendingを保持し、次回起動または次の計画実行時に再照合する。保存・照合に問題がある場合、元のreceiptと計画状態を確認し、先に私有DBの保存問題やwriter競合を解消する。同じticketを再使用しない。常時配送と操作者の専用復旧導線は後続接続として残す。

一件の配送は256 KiB、保存総量は1000件・8 MiBに制限する。容量上限では自動削除せずreceipt保存故障として扱い、成功へ変換しない。保持と容量回収の運用契約は未接続で、長期運転のQC対象。POSIXの私有directory／DB modeは700／600とし、Windows ACL・暗号化・trusted anchorの実証は別対象である。ローカル整合検査から改変不能や全履歴の完全性を主張しない。

## 実観測のM保存と後続step

計画file.searchの検証済み実結果だけを、Jが観測限定の記録として固定する。意味採用・世界真理・実行権限にはしない。元plan requestとstep審査request、元計画版、実結果・配送digest、出力、観測時刻と期限を保持する。C候補、意味更新案、資格、任意delete・上書きはこの入口の対象外。同検索の内部観測保存は限定契約であり、検索承認を任意の記憶変更や新作用へ再利用しない。

保存先はprivate-state/result-memoryのj-control.sqliteとm-state.sqlite。Jの計画checkpoint、J制御、Mは別取引であり、全体ACIDを仮定しない。J checkpointへMemoryCommit全文・更新ID・期待M版・内容digestをCAS保存してから、既存M取引へ配送する。同一内容だけをJの読取専用参照で照合し、Mのevent・次状態・ID消費・receiptを同時確定する。元Executor出力digestは保持し、Mのキー順を正規化した記録とは別のdigest契約として扱う。

M commit後にJ receipt保存または計画checkpoint保存が失敗しても、再起動時に保存済みの同commit・同receiptを照合する。期待版を再採番せず、確認済みを再applyしない。Jが配送本文を保全した場合はExecutor側をackできるが、ack直前にも現在のJ保存状態を再読し、読取失敗・CAS競合ではpendingを維持する。M recordとreceiptの同内容確認が終わるまで後続stepの審査・作用は保留する。J/M片方だけの欠落は新規初期化で確定へ戻さない。

認証済みsnapshotのresult_memory、memory_status、memory_content_digest、memory_receipt_digestは観測用だけ。raw観測本文・MemoryCommit・M receipt全文・ticketをUI、C、Complete Historyへ返さない。pending_or_unavailableの場合は私有保存先の可用性・整合・writer競合を確認し、同じ承認から再作用しない。起動時と計画審査前の同内容再照合は作用を呼ばない。現在M全体版が後続記録で進んでも、元recordと元receiptを照合し、古い観測の鮮度を延長しない。

この接続は観測保存と既存J依存consumerの範囲。一般意味採用、F-reference／Cへの引用、反証・解釈版更新、長期学習、常時復旧・容量解消・私有DBの運用復元・Windows ACLと5OS証拠は未接続または後段QC。局所のM保存を全体SYSTEM_SHAPED／QC／QAへ昇格しない。

今回の接続はBLUEのlocal Executor所有の記録である。Jの計画checkpointと実行DBは別取引であり、同時ACIDを仮定しない。認証済みJ↔D4Pocket Broker、独立した環境Permission、委任・目的版・実体版の全結合、外部受理の再照合、他作用と独立D4 Brokerとのreceipt再送調停、OS強制隔離と全process群停止、独立停止はBUILD_GAP。専用workerのprocess通信は独立D4 Broker Permissionを代替しない。旧L3は維持する。実provider・業務作用・別repo・installed／5OS・QC／QA・公開判断の証拠へ昇格しない。

実装・限定確認の履歴は[開発進捗](開発進捗.md)、次のconsumerと保留は[現行指示](IMPLEMENTATION_INSTRUCTIONS.md)を参照する。
