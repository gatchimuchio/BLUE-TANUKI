# BLUE-TANUKI QE作業標準要領

## 1. QEの上位原則

AGENTS.mdを共通規律、ownerが指定した最新版の非公開仕様書・工程表・施工指示書を設計・工程・施工の三点正本とする。2026-10-13の現行版は三点ともQE rev2.3。今後もowner指定の最新版を採用し、旧版は履歴として保持する。内部原典や要求対応表をPublic Gitに複製しない。

QEは全体設計→一気通貫のQE_BUILD→SYSTEM_SHAPED→BUILD_COVERED→実物全体のQE_QC（観測・欠陥・原因・改善・再検査）→対象別QE_QA→独立したowner GOの工程を包含する。198小単位（旧192＋Android/iOS各3）は実装の索引であり、198回の品質保証ゲートではない。

既存HDS-BRAIN、Approval Gate、L3 final review、監査、M非権限、秘密・実行環境Permission、fail-closed、復旧を全工程で維持する。未承認の外部作用はQCを待たず停止する。

## 2. BUILD_BATCHと毎小単位の再読

毎作業および各小単位の開始・切替・再開、セッション・担当の交代時に、最新版の三点セット（仕様書・工程表・施工指示書）すべてと適用AGENTS.mdを読み直す。ownerの現行指示、active指示、最新main HEADと差分、対象・目的・入力／出力・次consumerも再読して現在状態を再構成する。前回の読取結果、会話要約、記憶だけで今回の再読を代替しない。文脈切替の目的はドリフト抑止であり、モデル内部状態の消去保証ではない。

小単位の状態をCODE_PRESENT／WIRED／BUILD_GAP／BLOCKED_AUTHORITYで記録し、次consumerの接続を優先する。関連小単位を束ねて、実際の仕事が以前より先まで通る意味あるBUILD_BATCHを形成する。毎小単位に全体pnpm test、QC、QA、文書全面更新、Git二世代回転、commit/pushを強制しない。

調査のみのsubagentは並列化できるが、実装・正本更新・Gitのwriterは一つとする。他者の作業をreset／clean／revert／上書きで消さない。

## 3. 一気通貫実装と安全確認

Cは計算候補、J/HDSは委任目的の保持・採否・停止、Mは記憶・状態・根拠、D4Pocketの予定外殻を含む実行Brokerは現在のOS/Workspace Permission・対象・Owner承認を独立に扱う。Jの採用だけでBrokerの実行許可を発行したことにしない。

安全な試験仕事で、目的→C→J→環境許可→作用→結果→M→再計画・復帰・終了を通常経路で接続する。schema、fixture、UI表示だけの成功を仕事の完遂とみなさない。D4Pocketとミニドラの別repo変更は対象を限定した別委任が必要。

QE_BUILD中の確認は構文・型、必要なビルド、接続した実consumerの短時間疎通に限定する。Authority、秘密、Approval、監査、非冪等の外部作用に影響する変更は、その場で必要な拒否・安全停止の負例を確認する。既知の安全欠陥を放置して作用を有効化しない。全体回帰、耐久、性能、全OS、故障注入、競合比較の詳細検査はBUILD_COVERED後のQE_QCで行う。既存testやrelease gateの削除・恒久skipは禁止する。

## 4. Gitと証拠（D4Pocket方式）

main一本、単一writer、通常Windows/PowerShellで開発する。意味あるBUILD_BATCHまたは統治変更の編集前にlocal／remote HEAD、dirty差分、他writer、復元点を照合する。

ownerの2026-10-19指示により、D4-Pocket現行AGENTS.md §3.1の条件でGitHub Actionsを使用できる。用途はローカルにないOSのbuild、artifact生成、またはローカル検査だけでは不足する重い検査・testの補助に限り、triggerは`workflow_dispatch`のみとする。自動CI、push／pull_request／merge_group trigger、必須status check、CI greenによる完成判定は行わない。Actions結果は固定した対象commit上の補助証拠として扱う。

一時検証branchは対象commitの固定だけに使い、PRを作らない。失敗中commitをmainへ入れず、対象blockの検査が閉じた後に成功した正確なcommitをmainへfast-forwardし、remote HEADを照合して一時branchをlocal／remote双方で削除する。必要性、対象commit、trigger、結果、artifact、証明範囲と限界を記録する。workflow追加時はactive ROADMAPまたはphase instructionに目的を記載し、`workflow_dispatch`限定をlocal conformanceで検査する。BLUE固有の安全・Authority・Approval・Audit・release gate・owner GOは維持する。

**D4Pocketと同じ正規方式は、local復旧用branch二世代（refs/heads/codex/backup-main・refs/heads/codex/backup-main-prev）、remote backup tag二世代（refs/tags/codex/backup-main・refs/tags/codex/backup-main-prev）。** 編集前にlocal pairを回転し、旧remote tag SHAと照合したforce-with-leaseで二tagを保全し、実際のremote SHAを確認する。毎小単位の世代回転・commit/pushはしない。

**MIGRATION_COMPLETE（2026-10-12）：** 旧tagとremote backup branchの世代不一致を解消した。local recovery branch二本とremote backup tag二本は同じ世代を指し、旧remote backup branch二本はtagの実SHA照合後に競合検出付きで整理した。完了時SHAと手順はdocs/BACKUP_REF_MIGRATION.mdに記録する。

BUILD_BATCH末の技術確認後、限定commit/push、remote HEAD、tag二世代／未移行期間中のbranch二世代、作業ツリーを照合する。secret、credential、内部QE/HDS資料、実運転情報をPublic Gitに追加しない。過去SHAへresetしない。

証拠はCONFIG、INTERNAL_STATE、FIXTURE、LIVE_RUNTIME、EXTERNAL_EVIDENCEを区別する。実行結果とNOT_RUNを区別し、fixtureのPASSをinstalled製品や対象別QAの証拠にしない。

## 5. QC・QA・release

最終対応OSはWindows／Linux／macOS／Android／iOS。AndroidとiOSは別々のnative導入・OS権限・秘密・Device Link・仕事の接続・回復を要し、F16の「モバイル入出力」だけでは成立しない。設計はdocs/PLATFORM_TARGETS_QE.mdで扱い、実物のOS別QCは全体実装後に行う。旧RCのMobile未搭載と混同しない。

全体実装後のQE_QCでは、実物の機能・安全・停止・結果不明・復旧・長期運転・性能・OS差・競合機能を検査する。原因を設計・実装まで遡り、修正・再QCする。QE_QAは対象・版・OS・条件・証拠ごとにQA_SCOPED／QA_NOT_ESTABLISHED／OUT_OF_SCOPEを記録する。

現行旧v1.0 RCは1.0.0-rc.1、P13=PENDING_OWNER_GO、public_claim_allowed=false。出荷条件のGA／release bundle／実機・live／owner GOは維持する。旧P1–P12の局所成果を新AGIの品質保証へ転用しない。

## 6. 停止・記録とD4Pocket参照

ownerの2026-10-10「いいとこでストップ」による製品開発停止は規定同期自体では解除しない。後続の明示的な開発委任と最新正本・現物の再照合に従い、active指示の範囲でQE_BUILDを進める。C08.03実provider保留は継続する。D01.02は完了済みの局所履歴であり、新active実装ではない。

進捗は実際に通った仕事、次consumer、BUILD_GAP、安全停止、限定確認、復元点を中心に記録する。欠陥を原因（今回／既存／環境／未確定）とrelease影響（release_blocker／post_v1_scope／known_limitation）へ別軸分類する。

D4Pocketから共通原理として正本・現物照合、信頼境界、責任分離、証拠分類、単一writer、復旧を採用する。D4固有のFlutter/Rust/macOS手順とCLOSED結果は移植しない。手動Actions権限は自動移植せず、ownerの2026-10-19指示により、同repo現行AGENTS.md §3.1の使用条件だけをBLUE向けに適用する。
