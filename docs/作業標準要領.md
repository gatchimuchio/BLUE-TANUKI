# BLUE-TANUKI 作業標準要領

## 1. 目的と正本

本書は、要求の理解から実装、検証、復旧点の保存、公開同期、報告までを一つの作業として成立させるための要領である。[エージェント規定](../AGENTS.md) に従い、手順と記録の粒度を定める。作業量ではなく、要求された成果が根拠を伴って成立したことを完了とする。

製品の現在状態と実装権限は [有効な実装指示](IMPLEMENTATION_INSTRUCTIONS.md)、順序は [ロードマップ](ROADMAP.md) を読む。過去文書、他リポジトリ、検証結果だけで次工程の着手や公開を許可しない。本書の導入は J0 の再開、J1 の開始、P13 の owner GO を意味しない。

通常の編集・ビルド・テスト・起動・Git 操作は Windows / PowerShell で行う。WSL は Unix 実行属性を必要とする配布検証などの補助環境であり、通常開発の必須条件にしない。[開発環境](開発環境.md) の既存手順を使い、独自の pnpm wrapper や環境回避経路を作らない。

## 2. 着手と受入条件

1. 現在の owner 指示、適用される規定、日本語正本、実装指示を読み、到達状態と非対象を確定する。
2. Git の branch、remote、差分、同期状態、既存作業を確認する。既存差分を reset、revert、clean、上書きで消さない。
3. 関連するコード、契約、型、policy、capability、manifest、試験、検証スクリプト、運用文書を読む。指示された検索を行い、契約を消費する実経路と負例を特定する。
4. 対象を通常実行、制御、診断、修復・復旧、ビルド・配布、開発専用の経路に分類する。権限・承認・監査・公開・利用者の安全への影響を先に記録する。
5. 有限の受入条件と必須検証を定める。検証を通す前にバックアップ世代を回さず、編集前のmain HEADと開始時backup refsを記録する。

受入契約には、対象、非対象、条件、必要な証拠、必須コマンド、延期する追加保証と移送先を含める。専用の仕組みを増やす必要はなく、工程報告内の表でよい。

| 条件 ID | 成立させる状態 | 根拠・検証経路 | 状態 | 不成立時の対応 |
|---|---|---|---|---|
| 作業ごとに定める | 観測可能な有限の条件 | 実行コマンド、差分、証拠の所在 | `OPEN` / `FAIL` / `CLOSED` | 修正対象または具体的な阻害要因 |

`OPEN` は未確認、`FAIL` は不成立、`CLOSED` は必要な根拠を伴って成立した状態である。説明文、fixture の存在、成功という自己申告だけでは閉じない。

## 3. 検証後バックアップと Git 完結

詳細な順序は [エージェント規定 §21.7](../AGENTS.md#7-git-closure) を正本とする。ローカル作業ツリーが開発・品質判定の基準であり、GitHub は検証済み成果の記録・共有面である。

通常は `main` で一つの作業単位を実装・整理・検証した後、次の順序で閉じる。検証に失敗して修正を続ける間はbackup refsを回転させない。

1. 開始時に `git fetch origin --prune` を行い、local `main`、`origin/main`、作業ツリーをcleanかつ同期状態にする。他者の差分があれば帰属と意図を確認し、既存作業を消さない。
2. 検証完了後、現在の `codex/backup-main` を `codex/backup-main-prev` へforce-updateし、取得済みremote hashをleaseに指定してremoteへpushする。初回で `backup-main` が存在しない場合だけprev保存を省略する。
3. 今回commit前の `main` HEADを `codex/backup-main` へforce-updateし、remoteへforce pushする。どちらの操作も取得済みremote hashとの不一致を検出したら停止する。
4. 対象ファイルを明示してstageし、secret、credential、`.blue-tanuki/`、runtime state、一時物、debug outputが含まれないことを確認する。一作業単位を`main`へ一commitで保存し、直ちにpushする。
5. fetch後、remote `refs/heads/main` とlocal HEAD、`codex/backup-main` とcommit前main、`codex/backup-main-prev` と前世代backupの一致、clean状態を照合して記録する。

保持するbackup branchは `codex/backup-main` と `codex/backup-main-prev` の二本だけとする。tagへの置換、旧backup branchの削除、第三世代、phase別backup branch、backupからのPRを作らない。復旧点は新しい `codex/backup-main` が今回commit直前、`codex/backup-main-prev` がその一世代前である。local-only、監査のみ、commit / push禁止の明示指示がある場合だけGit統合を省略し、未同期範囲を報告する。

## 4. 実装と責任境界

広い仕様を広い変更の許可とみなさない。必要十分な差分に絞り、無関係な refactor、依存更新、推測上の機能、別の権限経路を追加しない。実装を伴う変更は試験・運用文書・変更履歴を同じ作業単位で整合させる。

| 責任 | BLUE-TANUKI の接続先と制約 |
|---|---|
| 判断・権限 | `packages/hds-brain`。standalone を保ち、LLM や UI に判断を委譲しない。 |
| 最終レビュー | 既存の Approval Gate、L1 / L2 / L3 と `FINAL_REVIEW_OPERATION_LIST`。並行リストや自己承認を作らない。 |
| 契約と適合性 | protocol、capability envelope、policy、manifest、既存 conformance。契約、拒否条件、実経路、検証の順に接続する。 |
| 下流の実行 | gateway、adapter、channel、plugin、tool、installer。宣言された範囲だけを実行し、外部 metadata から権限を作らない。 |
| 表示と入力 | Control Center、resident app、operator surface。状態、許容された digest / metadata、利用者の意思、次操作、復旧案内を扱う。権限判断・承認代替をしない。 |
| 結果・履歴・証拠 | OutputAudit、CompleteHistory、Runtime Invariants。既存の監査・非権限性・raw payload 非露出の契約を保つ。 |

契約を追加・変更するときは、消費する実経路、検証する経路、拒否・監査・`SUSPEND` すべき不正／未承認／未知／曖昧な入力、意図して未接続の範囲を特定する。契約定義や試験だけの存在を本番動作の証明にしない。

通常実行経路に doctor、setup、audit dump、repair、release verification、fixture、migration、debug helper を静的 import しない。必要な診断・修復は責任を分け、到達経路、権限範囲、失敗・復旧、検証を示す。host 摩擦を製品構造や検証の迂回で隠さない。

## 5. 検証と証拠

必須コマンドは [エージェント規定 §21.6](../AGENTS.md#6-validation) を正本とする。同節の適用範囲に従う最低検証、実装時の doctor / packaging、配布経路変更時の GA / bundle / verify、日本語基底変更時の gate、対象に応じた smoke を省略しない。有限の受入条件はこの最低基準を減らす理由にならない。

`.github/workflows` の workflow YAML は引き続き禁止する。D4 の手動 Actions 許可や一時検証 branch は採用しない。CI の成功を完成条件に置き換えない。

| 証拠源 | 観測するもの | 証明の限界 |
|---|---|---|
| `CONFIG` | 設定、manifest、文書、構成の照合 | 実行成功や導入済み製品の動作を証明しない。 |
| `INTERNAL_STATE` | process の内部状態、snapshot、局所 store | 外部サービスや別環境の動作を証明しない。 |
| `LIVE_RUNTIME` | 起動中の実経路を通る操作 | 実際に観測した経路・条件に限る。 |
| `EXTERNAL_EVIDENCE` | 展開した配布物、導入先、OS service、credentialed live smoke の証拠 | 対象の版・OS・構成・操作を記録し、未観測環境へ拡張しない。 |
| `FIXTURE` | mock、試験データ、単体試験の負例 | 契約論理や拒否挙動を確認する。本番接続や owner 承認を証明しない。 |

実行した正確なコマンド、版・環境、結果、証拠の所在、未実行理由を残す。失敗は「今回起因・既存・環境限定・未確定」に分類する。証拠不足を成功へ読み替えず、必要なら `SUSPEND` または公開阻害として扱う。

安全上重要な試験が実装と同じ定数・helper・fixture に依存し、誤りを見逃す懸念がある場合は、必要な範囲で意図的な変異による失敗確認を行う。対象、注入した変更、期待する失敗、観測結果、原状復帰、復帰後の検証を記録する。対象例は権限除去、L3 迂回防止、外部 metadata 非権限性、履歴の raw payload 除去、配布物の機密除外である。変異コードを commit しない。

## 6. 工程の閉鎖と最終品質保証

必要な受入条件がすべて `CLOSED` となり、整理・必須検証・Git 完結が済めば、その工程を閉じる。合格後に fixture、より強い証拠、仮説上の問題を際限なく追加して同じ工程を延長しない。再開には既存条件を壊す再現可能な回帰を必要とする。

受入範囲外の全体回帰、長時間運転、故障注入、性能、正式な導入済み製品の保証は、最終品質保証または承認済み後工程へ送る。移送先が未承認なら「最終品質保証・未承認」と記録し、勝手に開始したり完了扱いにしたりしない。

| 移送項目 | 元の条件・懸念 | 今回の必須条件ではない理由 | 移送先・必要証拠 | 公開への影響 |
|---|---|---|---|---|
| 具体的な追加保証 | 出典または観測事実 | 受入契約との差分 | 承認済み後工程または最終品質保証・未承認 | `blocks_release` と理由 |

安全・権限・承認・監査・復旧、既存の必須 gate、今回の条件を壊す観測済み不具合は移送して隠さない。必要な実機／導入先証拠が受入条件にある場合も、その証拠なしには閉じない。

テスト用 identity、隔離 fixture、既存の UI 自動操作などで成立する検証は、承認済み作業範囲で自律的に行う。試験用 identity と承認された実操作を区別し、実在 owner の承認、production credential、業務上の不可逆判断、公開 GO を捏造・代替しない。新しい工程への自動進行は禁止する。

## 7. 整理、残存項目、報告

完了前に今回導入した残骸、古い TODO、重複した規範、不要な抽象化、一時物を除く。関連する索引、工程指示、変更履歴、manifest、契約、運用案内、台帳を整合させる。日本語化した文書は意味と境界を審査し、移行負債からの除去と試験期待値を合わせる。既存負債文書を変更した場合も内容審査後に hash を更新する。

残存項目は原因分類とは別に、公開への影響を記録する。

| 分類 | 意味 | 必須記録 |
|---|---|---|
| `release_blocker` | 現行の公開条件を満たさない | 項目、理由、必要な対応、`blocks_release=true` |
| `post_v1_scope` | 現版の明示的な非対象 | 対象外の根拠、将来の採否、`blocks_release=false` である理由 |
| `known_limitation` | 観測済みで説明が必要な制限 | 影響、回避・復旧、必要な対応、`blocks_release` の判定理由 |

公開阻害を分類名だけで解消しない。必要な既知制限は [既知制限](KNOWN_LIMITATIONS.md)、[公開主張](../CLAIM.md)、[GA 基準](GA_BAR_DEFINITION.md) の該当箇所と整合させる。

最終報告はエージェント規定 §25 の項目を満たす。実装の存在、単体試験、適合試験、局所利用、配布物検証、実サービス接続、GA 基準、owner GO、公開許可を別の到達状態として報告する。文書や試験の変更だけで上位の状態を推定しない。
