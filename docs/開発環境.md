# Windows の開発環境と WSL の配布検証

この手順は、ソースを編集し、固定した依存関係からビルド・検証・局所起動を再現するための開発用手順である。[日本語基底規定](../規定/00_日本語基底規定.md)と [AGENTS.md](../AGENTS.md) に従う。今回の owner 指示により、通常の編集・ビルド・テスト・起動・Git 操作は Windows を標準とする。WSL は Unix の実行属性を必要とする配布生成・検証の補助環境であり、通常開発の必須条件ではない。製品の常駐インストール、外部サービスとの接続、署名、公開判定はそれぞれ別の経路で確認する。

## 使用する版

今回の Windows 開発環境は次の組合せで固定した。依存ライブラリは既存の `pnpm-lock.yaml` を使用し、環境構築を理由とする更新は行わない。

| 対象 | 版・条件 |
|---|---|
| Node.js | `22.23.3`、Windows x64 |
| Corepack | 上記 Node.js に同梱される `0.36.0` |
| pnpm | `package.json` 指定の `9.12.0` |
| 配布用 Python | `3.12.10`、管理用 uv `0.12.19`、実行できる `python3` コマンド |
| シェル | PowerShell。製品の `.cmd` 入口は Windows PowerShell 5.1 でも検証する |
| Git | HTTPS 接続、作業場所ごとの作者設定、LF を維持する設定 |
| Windows | シンボリックリンクを作成できる開発者モード、または同等の実行権限 |

Node.js は[公式配布](https://nodejs.org/dist/v22.23.3/)の `node-v22.23.3-win-x64.zip` を使用する。公式の `SHASUMS256.txt` と照合した SHA-256 は `2b0ff57b049cda1bbcea2240eec20467018713c1efe1f7360c2681859b90ed71`。開発用の版固定であり、製品の配布スクリプトが指定する Node.js `22.14.0` は変更しない。

## 初回準備

公式 ZIP を `%LOCALAPPDATA%\Programs\BLUE-TANUKI` に展開し、以下を PowerShell で実行する。展開先のディレクトリはユーザーの `Path` にも登録すると、新しいターミナルで使用できる。起動済みのアプリが古い環境を保持している場合は、次の先頭行で現在のシェルにも反映する。

```powershell
$env:Path = "$env:LOCALAPPDATA\Programs\BLUE-TANUKI\node-v22.23.3-win-x64;$env:Path"
node --version
corepack --version
corepack enable pnpm
corepack prepare pnpm@9.12.0 --activate
pnpm --version
```

新規取得では改行の自動変換を無効にしてから取得する。既存の作業場所で設定を変更するだけでは、すでに変換されたファイルの改行は戻らない。未保存の変更を保護し、原本と比較して扱う。

```powershell
git -c core.autocrlf=false clone https://github.com/gatchimuchio/BLUE-TANUKI.git
Set-Location BLUE-TANUKI
git config --local core.autocrlf false
git config --local core.eol lf
git config --local core.longpaths true
pnpm install --frozen-lockfile
```

日本語基底監査はファイル本文のハッシュを照合する。CRLF への自動変換を監査の失敗に合わせて台帳へ再登録してはならない。Git の作者名とメールアドレスは本人の設定を使い、秘密情報をリポジトリへ保存しない。

配布 ZIP の生成は Python を使用する。Windows のアプリ実行エイリアスだけが存在する場合、`where.exe python3` が成功しても Python 本体は実行できない。`python3 --version` まで確認する。今回の環境では、既存の Python 3.12 と uv を使い、[uv の標準の管理手順](https://docs.astral.sh/uv/guides/install-python/)で配布用の実体を別の場所へ導入した。

```powershell
# 初回のみ。Python 3.12 と py ランチャーが利用できる環境で実行する。
py -3.12 -m pip install uv==0.12.19
$env:UV_PYTHON_INSTALL_DIR = Join-Path $env:LOCALAPPDATA 'Programs\BLUE-TANUKI\python-managed'
$env:UV_PYTHON_BIN_DIR = Join-Path $env:LOCALAPPDATA 'Programs\BLUE-TANUKI\python-bin'
py -3.12 -m uv python install 3.12.10 --default
$env:Path = "$env:UV_PYTHON_BIN_DIR;$env:Path"
python3 --version
```

`--default` はこの uv 版では実験的オプションで、`python`・`python3` の実行ファイルを生成する。上記の専用ディレクトリをユーザーの `Path` で `Microsoft\WindowsApps` より前に登録する。既存の Python を既定のまま維持する場合、その Python の場所より後に登録する。配布検証を別シェルで再開したときも、`python3 --version` が実体の版を返すことを確認する。

復旧処理のテストは、本物のシンボリックリンクを作成して外部パスへの逸脱拒否を検査する。`EPERM` が出る場合は、[Microsoft の開発者モードの案内](https://learn.microsoft.com/windows/apps/get-started/enable-your-device-for-development)に従って有効化する。有効化には管理者確認が必要な場合がある。テストを削除・スキップして成功扱いしない。

## 検証の順序

リポジトリのルートで順番に実行する。`typecheck` は最後に生成済みの `dist` を削除するため、`build` より先に実行し、ビルドや起動と並列に実行しない。全テストは、ほかの重い検証と重ねずに実行する。

今回の 4 コア・8 論理プロセッサと OneDrive 上の作業場所では、既定の並列数による全体実行で、単独では通る doctor・復旧テストが時間切れになった。同時実行の負荷を抑えるため、既存の Vitest の環境変数で、このシェルの並列実行数だけを最大 2 にする。テスト対象、判定、制限時間は変更しない。別の実行環境で既定の並列数による成功を確認できた場合、この指定は不要である。

```powershell
$env:VITEST_MAX_FORKS = '2'
$env:VITEST_MIN_FORKS = '1'
pnpm typecheck
pnpm build
pnpm test
pnpm docs:check
pnpm validate:repo-health
pnpm validate:packaging
pnpm installer:verify
pnpm validate:ga
pnpm validate:product -- --phase P2 --evidence .codex-tmp/environment/product-evidence
```

最後のコマンドは WebChat の送受信、承認後の再開、HDS-BRAIN の単体動作、停止・権限昇格拒否、監査の連鎖を確認する。Windows では、このコマンド内の Linux 専用全テスト項目はスキップされるため、先に実行する `pnpm test` の成功を別に確認する。

`--phase P2` を省略すると、実インストールや自動起動設定を含む後続検査へ進む。[製品検証の手順](VALIDATE_PRODUCT.md)で実行対象を確認する。配布経路を変更した場合は、[AGENTS.md](../AGENTS.md) に従い `pnpm release:bundle` と `pnpm release:verify` も実行する。

## WSL の配布検証用補助環境

Windows では `wsl --install -d Ubuntu-24.04 --no-launch` で Ubuntu 24.04 LTS を準備する。自動初期設定を使う場合は、初回起動前に [Canonical の cloud-init 手順](https://ubuntu.com/wsl/docs/latest/howto/cloud-init/)に従って `%USERPROFILE%\.cloud-init\Ubuntu-24.04.user-data` を配置する。通常ユーザー、必要な OS パッケージ、既定ユーザーを設定し、既存の設定は上書きしない。導入後は `cloud-init status --wait` と `cloud-init schema --system`、`id`、`uname -r`、`findmnt -n -o FSTYPE /` で初期設定・通常ユーザー・WSL 2・ext4 を確認する。

必要な OS パッケージは `ca-certificates`、`curl`、`python3`、`tar`、`gzip`、`xz-utils`、`git`。OS パッケージの導入だけを管理者で行い、ソース取得、依存復元、ビルド、テストは通常ユーザーで行う。

以下は配布検証のために Ubuntu 内の Bash で一度実行する。Node.js は Windows と同じ `22.23.3` の Linux x64 版を使う。Windows 用の Node.js、pnpm、`node_modules` を共有しない。

```bash
mkdir -p "$HOME/.cache/blue-tanuki" "$HOME/.local/share/blue-tanuki"
cd "$HOME/.cache/blue-tanuki"
curl --fail --location --output node-v22.23.3-linux-x64.tar.xz \
  https://nodejs.org/dist/v22.23.3/node-v22.23.3-linux-x64.tar.xz
printf '%s  %s\n' \
  df450af89261115ef9f9e3830c3eeb2cc9213b63c720b1af623cb5dcbe2e02de \
  node-v22.23.3-linux-x64.tar.xz | sha256sum --check -
tar -xJf node-v22.23.3-linux-x64.tar.xz -C "$HOME/.local/share/blue-tanuki"
export PATH="$HOME/.local/share/blue-tanuki/node-v22.23.3-linux-x64/bin:$PATH"
export TMPDIR=/tmp
corepack enable pnpm
corepack prepare pnpm@9.12.0 --activate
```

上記の SHA-256 は [Node.js 公式チェックサム](https://nodejs.org/dist/v22.23.3/SHASUMS256.txt)との一致を確認した値である。補助環境のユーザーの `~/.profile` に同じ `PATH` と `TMPDIR=/tmp` を登録し、新しいログインシェルでも `node --version`、`corepack --version`、`pnpm --version` が固定版を返すことを確認する。

検証するソースは Windows 側の作業場所から `git archive` で受け渡す。commit 済みなら `HEAD`、未 commit の修正なら対象差分だけを確認・stage した後の `git write-tree` の値を指定する。未 stage の変更は含まれないため、検証対象との一致を確認する。Git の実行属性を維持し、秘密情報、`node_modules`、Windows 生成の配布物を含めない。

Linux の `/home` 以下の新しい検証ディレクトリへ展開し、その場所で次を実行する。`/mnt/c` は archive の受渡しに限って使う。このコピーを通常の編集場所にせず、修正と commit / push は Windows 側で行う。

```bash
findmnt -n -o FSTYPE -T "$PWD"
pnpm install --frozen-lockfile
pnpm build
pnpm validate:packaging
pnpm validate:ga
pnpm release:bundle
pnpm release:verify
```

`findmnt` は `ext4` を返すこと。配布スクリプトの Node.js archive cache は公式 SHA-256 との再照合があるため再利用できるが、生成済み payload や installer は再利用せず、空の `release/` から検証する。

### 全 OS の配布検証

全配布物の生成・検証は、リポジトリ推奨の WSL または Linux の ext4 上で実施する。Windows 上では Node.js の `chmod` で Unix の実行属性を保存できず、Linux/macOS 用単一ファイルの `package:installers:verify` が `installer is not executable` で停止する。これは Windows 上のアプリ実行や単体テストの成功とは別の、配布検証の未完了である。

Windows で生成した Unix 向け TAR 内にも実行属性の欠落が観測されたため、外側の単一ファイルだけを `chmod` して成功扱いしない。同じソースを Linux の `/home` 以下へ配置し、Linux 用の Node.js と pnpm で依存復元・ビルド後、`package:windows`、`package:unix`、`package:installers` と各 `:verify` を実行してから、`release:bundle`、`release:verify` を実行する。`/mnt/c` 上でのビルドや、既存成果物の存在による生成・検証のスキップで未完了を隠さない。

WSL が未導入なら [Microsoft の導入手順](https://learn.microsoft.com/windows/wsl/install)に従って準備する。Windows コンポーネントの追加で再起動が要求された場合、Linux の起動と検証が実際に成功するまで配布検証を完了扱いにしない。

## 局所起動

設定、トークン、セッション、監査データはソースや OneDrive 同期領域から分離する。初回だけ既存の設定生成コマンドを実行する。既存設定には `--force` を付けず、保持する。

```powershell
$devState = Join-Path $env:LOCALAPPDATA 'BLUE-TANUKI\development'
$devEnvFile = Join-Path $devState 'blue-tanuki.env'
pnpm run setup -- --yes --provider stub --host 127.0.0.1 --port 8787 --base-dir $devState --output $devEnvFile
pnpm run doctor -- --env-file $devEnvFile
pnpm gateway:serve -- --env-file $devEnvFile
```

起動後は `http://127.0.0.1:8787/app` を開く。停止は起動したターミナルで `Ctrl+C`。次回は `setup` を繰り返さず、設定先の変数定義と `gateway:serve` だけを実行する。ソースから直接実行する場合は、同じ設定を指定して `pnpm gateway:serve:dev -- --env-file $devEnvFile` を使う。

`stub` は外部 API を呼ばない開発用の応答であり、実モデルによる推論ではない。WebChat の操作画面で必要なトークンは設定ファイルから本人が入力する。値をチャット、検証ログ、Git に貼り付けない。起動時の設定先は絶対パスで指定し、pnpm による作業ディレクトリの変更で別の設定を作らない。

通常の doctor は未使用の外部連携を警告として表示する。開発環境の確認ではエラーがゼロであることと、各警告の意味を確認する。実モデルや外部チャネルの利用は、[認証情報の条件](CREDENTIAL_READINESS_MATRIX.md)を確認して別途設定・検証する。

## 完了の範囲

開発環境の成功は、その PC で編集・ビルド・テスト・局所起動を再現できることを意味する。Linux/macOS の実機検証、署名済み配布、外部 API の実通信、製品公開の承認を代替しない。

現在の製品は `1.0.0-rc.1`、P13 は `PENDING_OWNER_GO`、`public_claim_allowed=false`。日本語基底の通常監査の成功と、残存する移行負債を解消する厳格監査の成功も区別する。環境構築によって J1 以降や製品公開へ自動進行しない。
