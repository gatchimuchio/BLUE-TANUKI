# 計画候補・step選択・改訂の接続

2026-10-17、QEB-01-PLANSとQEB-01-RESULT-REFLECTIONの開発中経路。既存Developer入口から、計算Cの候補をHDSに保持し、明示した一stepを既存Approval GateとExecutorへ渡す。加えて、同一owner/channel・現行計画版の受領済みfile.search観測から限定射影を作り、Cの解釈候補をJが表示前に照合する。自動目的採否、一般的な意味採用、汎用Broker、仕事全体の完遂、製品QC／QAは未成立。

## 操作する入口

Control CenterのDeveloper入力、または認証済みPOST `/operators/developer/invoke` のcontentで操作する。同じ接続のuserとchannelに保持した計画だけを選択・改訂できる。共有tokenとcaller指定userの既存入口であり、個人identity認証の成立を意味しない。

1. `plan:compute <目的と対象>` は計画候補をCへ求める。固定request IDを計算へ渡し、既知commandの結果から構造適合した未実行候補だけを保持する。offline stubはecho専用のため、計画を生成した証拠にはならない。
2. GET `/runtime/snapshot` の `hds.operation_plans` でplan ID、revision digest、step ID、対応状態を確認する。plan／step IDはproviderの原文を出さないdigest handle。原文の引数・対象・結果はこの射影へ出さない。
3. `plan:review {"plan_id":"<handle>","revision_digest":"<現在のdigest>","step_id":"<handle>"}` で一stepを指定する。現状の実resolverはfile.searchのdirectory targetとparameters.rootが一致するもの。依存の検証済み結果と期限を再照合し、HDSが現在の具体内容からcommandを作る。
4. 現在のoperationと承認modeに従う。既知file.searchはL1_observeで、ask_every_timeなら承認画面で確認する。planに書かれたpermissionは承認の代替ではなく、未知tool.callや他のL3操作はfull accessでも最終レビューを迂回しない。
5. `plan:revise {"plan_id":"<handle>","expected_revision_digest":"<現在のdigest>","plan":<改訂した全候補>}` は旧版を残して未実行部分を改訂する。変更と依存影響がある旧pending commandだけを失効する。試行済みstepとその依存影響の変更は拒否する。

候補本文の元のplan／step IDも指定できるが、曖昧な対応は拒否する。改訂候補のplan/request IDは保持済みのものを維持する。計算が申告したapproved／succeededやresult_digestを実行事実へ昇格させない。

## 受領済み観測から解釈候補を表示する

`plan:reflect {"plan_id":"<handle>","revision_digest":"<現在のdigest>","step_ids":["<step handle>"],"question":"この観測で何が言えて、何が未確認か"}` は、現在の計画版にある1〜8件のstepの受領済み結果を対象にする。全stepについて同一owner/channel、現行revision、verified binding、Jに保存されたMemoryCommitとreceipt、Mの同一record、元観測期限を照合できない場合はCへ進めない。現状はfile.search観測だけを扱う。開発smokeは1件を使う。

JがCへ渡すのはrecord・receipt・revisionのdigest、検索の件数・走査数、観測時刻・期限などであり、raw検索結果、path、ticket、session history、LTMを渡さない。Cの出力は指定recordへの解釈と不確実性の候補に限る。provider／model／requestと資源上限、入力・出力digestを検査し、返答の引用先と内容が元projectionに一致することをJが表示直前に再照合する。

この表示は意味の採用、世界真理、反証済み、計画変更、実行許可、M更新を意味しない。候補が拒否された場合は固定文だけを表示し、記憶・作用を変更しない。`pnpm exec tsx scripts/smoke_operation_plan.ts --reflection` はloopback合成Cと実file.searchを使い、表示前J照合とM revision不変を確認する開発用smokeであり、実provider試験や全体QC／QAではない。

## 回復状態と実結果

`BLUE_TANUKI_STATE_ROOT` の既定は起動時の `.blue-tanuki`。その `private-state/operation-plans/j-state.sqlite` に計画原文、内部command対応、検証済み依存結果を保存する。通常file toolのworkspaceとは独立し、private-stateは通常の検索・書込・編集から拒否する。aliasの実pathとsandbox root指定でも同じ保護を行う。私有運転状態をGitへ追加しない。

実行直前にcommand全体、現在のprepared内容、依存鮮度を照合し、開始意思をSQLiteへCAS保存してから、承認済みcommandを深く固定してExecutorへ渡す。CAS競合・保存失敗では実行へ進まない。既存結果契約のplan_step_binding=unboundは維持し、HDS内部の対応から計画へ帰属させる。

今回の結果検証は、実output全体とresult_equalsの期待値・対象を照合する有限経路。Cが与えた期待値の意味的妥当性や外部postconditionを保証したものではない。内部の準備有効期間は10分。期限を過ぎた依存結果で新しい作用を開始しない。

再起動では未実行の旧pendingを失効し、開始意思だけが残る試行はoutcome_unknownとして再実行しない。これはプロセス間CASと一時領域の回復疎通であり、全故障・耐久QCではない。

## 拒否時の次の操作

- plan_revision_changed：現在の射影を読み、改訂版の具体内容を再確認して選び直す。
- plan_step_not_ready：依存結果・期限・未接続の前提を確認する。過去の成功表示だけで進めない。
- plan_step_already_selected_or_attempted：既存対応と結果を確認する。結果不明の試行を重複実行しない。
- plan_target_resolver_not_connected：対象resolverは未接続。別の生commandへ自動fallbackしない。
- plan_control_requires_fresh_review：SUSPENDした計画操作はresumeから実行せず、原因を修復し新しいreviewを行う。
- plan_state_or_command_binding_failed：保存先・容量・別writerを確認する。DBを通常file toolで修復・改変しない。

開発専用の `pnpm exec tsx scripts/smoke_operation_plan.ts` は、専用loopback合成C、実file.search、一時保存先とask_every_timeだけでHTTP接続・承認失効・改訂・再起動を確認する。実provider、credential、外部業務作用、D4Pocket／ミニドラの変更、installed製品、全OSの証拠ではない。
