# BLUE-TANUKI 日本語基底規定

規定版: 1.0.0
成立日: 2026-09-01
状態: 成立・適用中

## 1. 目的

BLUE-TANUKI の対象、目的、境界、関係、判断、仕様、実装、監査、公開を、日本語で最初に形成し、日本語から検証可能にする。日本語は表示上の優先言語ではなく、意味と規範を成立させる唯一の基底規定言語である。

## 2. 適用範囲

本規定はリポジトリ内の全資産に適用する。文書だけでなく、設計、ソースコード、コメント、利用者向け文言、設定、テスト、監査証拠、配布物、機械可読契約、ファイル名、外部連携境界を含む。

バイナリ、構文、識別子など自然言語として意味を形成しない要素まで日本語文字へ置換することは要求しない。ただし、それらが指し示す意味、採否、責任境界、例外理由は日本語正本へ接続しなければならない。

## 3. 成立順序

新しい対象や変更は、原則として次の順序で成立させる。

1. 日本語で対象を指し、他の対象との差を捉え、関係を置く。
2. 日本語で目的、境界、成功条件、失敗条件、権限、検証方法を定める。
3. 日本語で定義と構造を記録する。
4. 日本語で反例、矛盾、未確認事項、局所例外の必要性を監査する。
5. 日本語正本として採否し、索引へ接続する。
6. 実務上必要な範囲に限って、外部言語・構文・識別子へ局所投影する。

既存の英語文を先に正本として置き、その逐語訳を日本語正本とみなしてはならない。外部語から日本語の意味を逆定義してはならない。

## 4. 正本と投影

- 日本語正本は、同じ対象に関する多言語投影より優先する。
- 翻訳、外部 API 名、型名、環境変数、CLI、商品名、論文名、引用は、それだけでは規範的意味を持たない。
- 多言語投影は日本語正本の意味を増減、反転、上書きしてはならない。
- 日本語正本と投影が矛盾する場合は、実行を安全側へ停止し、日本語正本または局所例外を再監査する。
- HDS-BRAIN、Approval Gate など既存の機械識別子・固有名は、日本語で成立した概念を参照するラベルであり、意味の供給源ではない。

## 5. 局所例外

多言語は、実務上やむを得ない場合に限り、必要最小の箇所へ局所例外として認める。例外は `局所例外台帳.json` に次を記録して初めて成立する。

- 一意な例外識別子
- 正確なパスと対象領域
- 外部言語または外部形式
- 回避不能な理由
- 対応する日本語正本
- 権限・意味への影響がないこと
- 再審査条件

次は例外理由にならない。

- 業界では英語が普通であること
- 英語資料が多いこと
- 後で翻訳しやすいこと
- 既に英語で書かれていること
- 移行量が多いこと
- 実装者や LLM にとって便利であること

許容し得る理由は、外部 API・プロトコル・規格との互換、プログラミング言語の構文、ライブラリ・型・環境変数・CLI の固定識別子、固有名、原文引用、法的原文、検索・監査再現性、外部システムとの相互運用などである。それでも例外範囲は必要部分に限定する。

## 6. 移行負債

既存の非日本語資産は、自動的に局所例外とはならない。実務上不可避と立証できないものは `移行台帳.json` に未解消負債として記録する。

- 通常監査は、登録済み負債の同一性と未登録負債の不在を確認する。
- 登録済み負債の無審査変更は拒否する。
- 新しい非日本語負債の追加は拒否する。
- 厳格監査は、負債が一件でも残る間は失敗する。
- 負債の存在中は日本語基底の「規定成立」と「全資産移行完了」を区別する。

## 7. BLUE-TANUKI の安全境界

本規定は言語を理由に、次を変更または弱化しない。

- HDS-BRAIN が上流の判断・権限基盤であること
- 人間の owner が最終責任と明示的 GO を保持すること
- LLM、ツール、cron、チャネル、外部メタデータが下流であること
- Approval Gate と最終レビュー境界
- hash-chain audit と完全履歴の証拠性
- Runtime Invariants と fail-closed / SUSPEND
- Layer A / Layer B、first-party / preview / reserved の境界
- `used_for_authority=false` の証拠・記憶・外部参照
- `public_claim_allowed=false` の P13 pre-GO 状態

翻訳で安全境界の強さが不明になった場合は、成立したとは扱わない。

## 8. 監査

監査は日本語文字の有無や比率だけを合否根拠にしない。文字比率は未確認資産を発見するための信号に限る。合否は少なくとも次を確認する。

- 意味が日本語で先に成立しているか
- 規範的権限が日本語正本へ接続しているか
- 多言語箇所が真に不可避か
- 例外が局所化され、台帳に記録されているか
- 識別子が日本語意味を逆定義していないか
- 既存の移行負債が増加・変質していないか
- 安全・承認・監査・公開境界が維持されているか

`scripts/japanese_base_gate.ts` はこの監査の機械投影であり、規定そのものではない。ゲートと本規定が食い違う場合は、ゲートを安全側へ修正する。

## 9. 自己適用と再開放

本規定自身も有限で暫定的な Projection である。反例、意味欠落、外部境界の変更、監査不能性が見つかった場合は、日本語で理由と影響を記録し、規定を再開放する。再開放は既存の証拠や不都合な反例を消去する権限を与えない。
