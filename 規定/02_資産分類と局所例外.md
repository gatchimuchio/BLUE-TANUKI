# 資産分類と多言語局所例外

## 1. 全資産の分類

BLUE-TANUKI の全資産は、少なくとも次のいずれかとして扱う。

| 分類 | 規範性 | 日本語基底の要求 |
|---|---:|---|
| 日本語正本 | あり | 意味、境界、採否、検証を日本語で成立させる。 |
| 日本語からの実装投影 | 正本に従属 | コード、設定、テスト、UI を日本語正本へ追跡可能にする。 |
| 機械構文・識別子 | 単独ではなし | 互換性上必要な形を維持し、日本語意味を逆定義しない。 |
| 局所的な多言語投影 | 正本に従属 | 不可避性、範囲、日本語参照、再審査条件を台帳化する。 |
| 履歴・原文証拠 | なし | 同一性保持のため原文を保存し、現行仕様へ昇格させない。 |
| 移行負債 | 未成立 | 例外扱いせず固定・可視化し、日本語正本化まで厳格合格を拒否する。 |
| バイナリ・生成物 | 単独ではなし | 生成元、用途、検証方法を日本語正本へ接続する。 |

## 2. 自然言語と機械要素の境界

プログラミング言語の予約語、型・関数・パッケージ名、API フィールド、環境変数、CLI オプション、プロトコル値、ファイル形式は、自然言語の正本ではなく機械参照である。これらを一律に日本語識別子へ変える必要はない。

一方、次は自然言語上の意味を持つため本規定の対象である。

- 利用者へ表示する説明、警告、失敗理由、承認理由
- コードコメントや JSDoc による設計・制約説明
- README、仕様、手順、監査報告、リリース判断
- JSON 等に格納された人間向け説明、主張、理由
- テスト名が仕様や安全境界の唯一の記述になっている場合のその意味

## 3. 局所例外の採否

局所例外は「日本語化できない」ことではなく、「日本語化すると外部互換、証拠同一性、法的原文、検索再現性などの必要条件を損なう」ことを示す。例外を広いディレクトリへ適用する場合でも、対象領域は原文証拠本文などに限定し、そこで生まれる新しい現行仕様までは覆わない。

採用時に確認する。

1. 日本語正本が先に存在するか。
2. 外部言語が本当に回避不能か。
3. 行、フィールド、ファイル、限定ディレクトリのいずれかまで局所化されているか。
4. 例外を除いても同じ機能・監査再現性を維持できないか。
5. 例外箇所が権限、承認、公開判断を独自に定義していないか。
6. 再審査条件が具体的か。

## 4. 履歴証拠

`docs/history/` の過去文書、完了済み phase 報告、既発行リリースノートは、当時の証拠として原文を保つことがある。それらは現行正本ではなく `used_for_authority=false` である。現行仕様が必要なら日本語正本側へ新たに成立させ、履歴文書を編集して現在を装わない。

## 5. 移行状態

機械監査の第一段階は Markdown の規範的散文を対象にする。ソースコード中の利用者向け文言、コメント、HTML の `lang`、インストーラー表示などは本規定の適用外ではなく、後続の日本語正本化で監査面を拡張する対象である。

したがって現在は次を区別する。

- 全リポジトリを日本語基底で規定した: 成立
- Markdown 活正文書の未登録増加を防止した: 成立
- 全 Markdown 活正文書を日本語正本化した: 未完了
- 全 UI・コード内散文を日本語正本化した: 未完了

未完了を局所例外へ読み替えてはならない。
